### 两处偏离的解读

1. **读速 0.44 MB/s**：10 MHz SPI 理论峰值 1.25 MB/s，实测 35% —— sdspi（1 线）+ FAT 层 + 每块开销的正常水位，
   不是我原来按 1.25 MB/s 算的「~3 s」。后果是硬的，见下面的启动时间线。
2. **14 px 冷栅格 878 µs**：热命中 19.48 µs 与 ADR 0016 的 19.7 µs 几乎相同 ⇒ 不是包装层（scoped_glyph_bitmap）
   的开销，差异在「第一次栅格化」这条路上。最可能的原因是**字体源位置变了**：spike 那次数的是 flash mmap（XIP 走
   缓存），产品现在是 PSRAM 里常驻的 3.85 MB —— stbtt 逐字读字形轮廓时，PSRAM 随机读比 XIP 缓存慢。
   这条是**推断，没做 A/B 验证**（要验证得让探针再建一个从 flash 读的实例）。

## 收到用户决定之后：接受 8.9 s，加启动占位屏（2026-10-17 21:4x）

用户拍板走「D · 接受 + 占位屏」。实现在 `app/common/aidogui_ui_bridge.cpp`：

- `splash_begin()` 在读 TTF **之前**建一块占位屏（内置 embark_zh_14 画 `EMBARK` + 150×8 进度条 + 百分数），
  `lv_refr_now()` 先推上面板，再进阻塞读。文案只用 ASCII —— 此刻 TTF 还没进内存，
  「正在加载字体」里的字不在那 184 个字形里，会画成方框。
- `read_ttf()` 从「一次 fread 3.85 MB」改成分块（256 KB/块），每块 `splash_progress()` 更新进度条。
- `splash_end()` 在字体建好后还原上一屏并删掉占位屏；init 里另打一行「字体加载用时 N ms」当证据。

真机验证（`hw/boot-splash.log`，逐行时间戳）：

| 时刻 | 事件 |
| --- | --- |
| 1253.1 ms | 字体缓存配额合计 120832 字节 |
| 10438.8 ms | 字体源读进来（3,854,132 字节） |
| 10562.9 ms | `AiDoGUI 字体加载用时 9254 ms（这段时间面板上是启动占位屏）` |
| 10563.0 ms | 7/7 已加载 |
| 10624.7 ms | App clock onCreate |
| 10999.3 ms | `[AUTODEBUG_PASS] SD_FONT_OK` |

→ 进度刷新（15 次 = 16 个 256 KB 块）总共多花约 320 ms（9,254 − 8,932），换来 9 秒里屏上不是黑屏。
**面板上到底长什么样没有机检通道**，第一次开机请人眼确认。

宿主侧：构建通过、ctest 2/2、五条故事全绿（字体加载用时 14–19 ms，占位屏一闪而过）；
clang-format clean；真机 TU 校验 OK；固件 0xe6b80（945,024 B）。

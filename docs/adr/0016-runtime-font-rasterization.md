# 字体运行期栅格化：删掉离线 BIN 子集，改用 lv_tiny_ttf + flash 映射整份 TTF

**状态**：已定（spike 已出数）。**落地方式已被 ADR 0017 取代**：第 2 条（TTF 进 4 MB flash 分区 + mmap）
与第 5 条（字体随固件分发）作废，改为「SD 卡上的整份 TTF + 常驻 PSRAM」；第 1、3、4 条继续有效。
**本文的实测数据仍然有效**，被 ADR 0017 直接引用（改的只是"字从哪来、几档、多少缓存"）。
取代 ADR 0007 的第 1、4 两条（"静态子集烧 flash 为主"与"FreeType 推迟"）；其第 3、5 条由 ADR 0017 取代。

## 背景与触发

今天 UI 的字库是**构建期产物**：设计器导出 7 个 BIN 子集（11/12/14/22/28/48/56 px，合计 68,700 字节），
用 `tools/aidogui/gen_fonts_bin.mjs` 按"所有屏的文案 + app/<屏>/ 源码里的字符串"求并集补字，再把 BIN 拷到
SD 卡 `fonts/`。这条链有三个硬伤：

1. **每加一个字都要重新导出 + 重新拷卡**，而"忘了拷卡"是静默失败：2026-10-17 真机实测，卡上 14px BIN 是
   git HEAD 版本（17,812 字节），而工作区导出已是 18,856 字节 —— `font_service` 用**文件字节数**记账，
   于是串口打出的是 17,812，字库确实装了，只是少了新加的字；新屏上的"关于/平台/字库/对时"会画成方框，
   **宿主任一验收都通过**。
2. **字符集是构建期闭集**。歌名、书名、电台名、新闻标题是运行期文本，不可枚举；小说阅读器更是整本书。
3. 账面还多一层"第 5 处注册点"：`gen_fonts_bin.mjs` 里手写的屏→源码目录表，漏一行就静默缺字。

## 结论（一句话）

**可行，而且比现在的 BIN 更快。** 三块判据全部通过，两个反直觉的数字：

- 一屏 120 个不同汉字（14 px），运行时栅格化首帧 **56.8 ms**、热帧 **35.6 ms**；同样一屏用卡上 BIN
  是 **128.5 / 123.0 ms**（BIN 用的是 4 bpp，LVGL 的 4 bpp 混合路径比 8 bpp 慢约 3 倍/像素 ——
  这条本身值得单独记一笔：就算抱着 BIN 不放，改成 8 bpp 也能快 2 倍，代价是体积翻倍）。
- 字形缓存放 PSRAM 还是内部 RAM **几乎没差别**（56.8 vs 56.0 ms），所以缓存可以直接吃 PSRAM 字库区，
  不必去挤 40 KB 的静态池。

## 实测数据

宿主（x86，`.scratch/embark-v1/spikes/font-runtime/`，`-DEMBARK_BUILD_FONT_SPIKE=ON`）：

| 指标 | BIN 子集 | 运行时栅格化 |
| --- | --- | --- |
| 冷栅格 | —（预生成） | **13.2 µs/字** |
| 热命中 | — | 0.37 µs/字 |
| 一屏 150 字，首帧 | 1.08 ms | 4.45 ms |
| 字形位图内存（150 字 / 14 px） | 约 21 KB（4 bpp，flash 里） | 约 31 KB（8 bpp，堆上） |
| 判据：`adv_w` 偏差 | — | 264 个码点**全部 0** |
| 判据：`line_height` / `base_line` | 16 / 3 | **16 / 3（完全一致）** |
| 判据：墨量（48×48 平均亮度） | 20.90 | 20.93（**比值 1.001**，单字 0.995–1.008） |
| 判据：包围盒 | U+4E2D 13×11 | 15×14（+1~3 px 的**透明边**，见下） |

判据"逐字包围盒偏差 ≤1 px"是错的代理指标：stb 的 `stbtt_GetGlyphBitmapBox` 向外取整，多出来的
是看不见的透明边，异像素只占 48×48 的 1.8%–5.8% 且全部在笔画边缘；**字重（墨量）与排布（adv_w/
line_height）才是要守的**，三项全过。对照图 `.scratch/fonttest/glyph_compare.png`。

真机（ESP32-S3，`DEMBARK_FONT_PROBE=ON`，串口日志 `.scratch/fonttest/devprobe7.log`）：

| 指标 | 数值 |
| --- | --- |
| flash 分区 mmap 3.85 MB TTF | **162–167 µs**（零 RAM 占用） |
| 建 14 px 字体实例（cache 40 KB） | 130 µs |
| `line_height` / `base_line` | 16 / 3（与宿主、与 BIN 一致） |
| 冷栅格（缓存 PSRAM） | **405.6 µs/字** |
| 冷栅格（缓存内部 RAM） | 501.3 µs/字 |
| 热命中 | **19.7 µs/字** |
| 一屏 120 字 14 px 首帧 / 热帧（PSRAM 缓存） | **56.8 / 35.6 ms** |
| 一屏 120 字 14 px 首帧 / 热帧（内部 RAM 缓存） | 56.0 / 34.7 ms |
| 同一屏用卡上 BIN（4 bpp） | 128.5 / 123.0 ms |
| 同一屏用内置 montserrat（120 个 'A'，纯绘制本底） | 29.6 / 26.3 ms |

**一次翻车与它的教训**（写进本文档是因为它会被再踩一次）：第一版把字形缓存给了 64 KB，而当时字库区
只剩 59 KB 空闲 —— 每次插入位图都会触发 LRU 淘汰，于是**每一帧都在重新栅格化**：首帧 716 ms、热帧
699 ms，看起来像"CPU 撑不住"，其实只是缓存预算没小于可用池。同一版本还在 `stbtt__new_active` 里
malloc 失败直接 assert 复位（6 次重启循环）。⇒ **缓存预算必须由"可用池 − 余量"反推，且分配失败要
降级（丢最旧、退回内置字体），不能让它撞 assert。**

## 决策

1. **删掉 BIN 链**：`tools/aidogui/gen_fonts_bin.mjs`（315 行）、补字并集逻辑、`export/font/*.bin`、
   `font_service` 里按文件字节数记账那一段、`export.ps1` 的 `gen_fonts_bin` 调用。设计器导出改为只出
   UI 代码与图片（`imageOutputFormat` 保持 BIN），字体配置只影响设计器里的预览。
2. **TTF 进 flash 分区**，不常驻 RAM：`partitions.csv` 新增 `fonts, data, 0x40, 0x310000, 4M`
   （16 MB flash，factory 结束于 0x310000，下一个空闲 0x710000），启动时 `esp_partition_mmap` 一次，
   约 165 µs，之后按需读。
3. **字形缓存放 PSRAM 字库区**，预算由分区剩余内存反推（14 px / 150 字 ≈ 37 KB；22 px 约 4 倍）。
   保留"字库记账"的概念，但记账对象是**缓存字节**而不是 BIN 文件；加载失败降级到内置 `embark_zh_14`
   并 `ELOG_WARN`，不 assert。
4. **字号仍来自设计稿**：`lv_tiny_ttf_create_data_ex(data, size, px, cache)` 只用 7 档字号中的实际使用者；
   宿主与真机同一份代码，差异只在字体来源（宿主读文件、真机读分区）。
5. **删掉"卡上 BIN 与仓库不一致"这一整类 bug**：字体不再是分发物，改由固件携带（分区随固件烧录）。

## 代价与影响（诚实账单）

- **首次出现代价**：400 µs/字。小说阅读器一页约 300 个不同字 ⇒ 首屏约 120 ms；翻页大概率热命中
  （19.7 µs/字）。可接受，但需要"进 App 预热常用字"或"翻页时先渲染后滚动"。
- **内存**：8 bpp 是 4 bpp 的两倍。14 px 150 字 37 KB、22 px 同字数约 150 KB ⇒ 22 px 全屏会超出当前
  131 KB 字库区，需要"大字号缓存小一点 + 淘汰"或扩容字库区（PSRAM 余 8.2 MB，代价不是容量而是碎片）。
- **度量校准**：`adv_w`/基线已在宿主与真机双向核对一致，但**7 档字号要逐档核对**（本次只核了 14 px）。
- **字重**：stb 无 hinting 调整，14 px 实测墨量差 0.1%，可接受；11/12 px 小字号需复测（更容易发虚）。
- **商业授权**：`ui_heiti.ttf`（时尚中黑简体 TRENDS）授权待确认。整份 TTF 进固件 = 3.85 MB 的字符数据
  随机附在设备里，暴露面比"子集位图"大得多，**必须先拿到授权或换开源字体（思源黑体 / Noto Sans SC）**。
- **多语言/复杂书写系统**仍是另一件事：阿拉伯文要 bidi、天城文要 shaping，stb 都不给；真要那天再议
  HarfBuzz 级别的东西。

## 否决过的方案

- **继续用 BIN，只把字集铺满**：全字集 7,582 字 × 7 档 4 bpp ≈ 26 MB，且**完全不防**"卡上旧文件"那条；
  真瓶颈是 PSRAM 池（131 KB）与开机读盘，不是 SD 容量。
- **FreeType**：库不在仓、要交叉编译、体积与缓存都比 stb 大一档；需要的是"任意 Unicode 文本"，
  stb 单头 MIT 就够。
- **把 TTF 常驻 PSRAM**：3.85 MB × 常驻，换不来任何东西（stb 无流式 API，但 flash 映射已经解决了
  "随机读"）。

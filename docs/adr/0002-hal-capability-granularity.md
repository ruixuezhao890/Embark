# HAL 只抽象到芯片能力粒度

> 已被 [0019](0019-service-layer-and-public-hardware.md) 取代（2026-10-18）：服务层与网络/音频/姿态
> 进入框架范围。本文仅作决策史保留 —— **下面「网络与 OTA 不在 v1 范围内」这句已经不是现行规则**。

HAL 只暴露"芯片能做什么"——显示输出、输入事件、时间、持久化、日志后端、系统控制；总线只给最薄的原始读写接口。不做设备驱动，不做传感器抽象，网络与 OTA 不在 v1 范围内。

这样定的理由：HAL 的价值在于换平台时只替换后端。一旦开始抽象具体外设，接口就会被某颗芯片的细节绑死，可移植性反而下降。代价是上层要用某个具体外设时，需要自己在 App 侧或平台侧实现驱动——这是有意接受的成本，不是遗漏。

---

**2026-10-18 更正（现行规则以 [0019](0019-service-layer-and-public-hardware.md) 为准）**：

- 上面这条「不做设备驱动 / 网络不在范围内」**已被推翻**。HAL 之上加了一层**服务层**
  （设备服务 + 公共资源：`IImu` / `IAudio` / `INetwork` / `IGpio`），业务服务仍不进基建。
- 本文最有价值的那句判据**保留并上移了一层**：「接口不能被某颗芯片的细节绑死」→
  硬规则 **HAL 里不许出现芯片型号名**（`IImu` 可以、`IQmi8658` 不行），禁令的作用范围从
  「HAL 层」扩到「服务接口层」。
- 所以本文不是「错的」，是**范围变了**：HAL 那一层的粒度决定仍然有效（只到芯片能力、不做驱动），
  变的是「框架要不要有服务层」这一问。

# 服务层：HAL 之上放「设备服务 + 公共资源」，业务不进基建

> 2026-10-18 立项。取代 [0002](0002-hal-capability-granularity.md)（该文把「网络与 OTA 不在 v1 范围」
> 写死，与本文相反）。落地拆在 `.scratch/app-platform/issues/07-service-layer.md`（骨架）、
> `08-imu.md`、`09-audio.md`、`10-network.md`。
> **2026-10-18 更新**：07 号票已落地骨架 —— `hal::Context` 从 8 个成员变成 11 个（末尾三个可空服务槽
> `imu` / `audio` / `network`，三个装配点已补齐）。
> **08 号票已落地 `IImu`**：`core/include/embark/hal/imu.h` 定义 `ImuSample` + `IImu`，
> 宿主（`host/host_imu.*`，可复现合成曲线）与真机（`device/src/esp32_imu.*`，
> 板载六轴、地址运行期探）两侧都已接进 `Context::imu`。
> > **09 号票已落地 `IAudio`**：`core/include/embark/hal/audio.h` 定义 `AudioState` + `IAudio`
> （`play(path)` / `pause` / `resume` / `stop` / `seek` / `position_ms` / `duration_ms` /
> `set_volume`），**本层只认 PCM WAV**（MP3 要引解码器，另开一票）；音量是软件采样衰减
> （板载 DAC 控制接口是 HW，没有寄存器）。宿主 SDL 与真机 I2S 两侧都已接进 `Context::audio`。
> **10 号票已落地 `INetwork`**：`core/include/embark/hal/network.h` 定义 `NetState` + `INetwork`
> （`state` / `connect` / `disconnect` / `http_get` / `sntp_sync` / `last_http_status`），
> **只做明文 HTTP**（https 返回 `unsupported`：要么引 TLS，要么走代理，另开一票）；凭据只存内存、
> 不落 NVS。宿主 socket 后端与真机 esp_wifi 后端两侧都已接进 `Context::network`。
> 至此 07/08/09/10 四票全部落地，服务层骨架与三块硬件能力齐了。决策与规则不变。

## 背景

用户要的是「AI 把硬件基础设施做好，我自己写 App 逻辑与界面，像在电脑上开发应用一样」
（`.scratch/app-platform/spec.md` 的目标段）。这份诉求把「公共硬件资源」变成基建的一部分：
WiFi、屏幕、IMU、音频这些**每台设备都有的东西**，不该由每个 App 各自写一遍驱动 ——
那正是用户想省掉的 token 成本。

而 [ADR 0002](0002-hal-capability-granularity.md) 当时把这个方向**明确排除了**：

> 不做设备驱动，不做传感器抽象，网络与 OTA 不在 v1 范围内。
> 代价是上层要用某个具体外设时，需要自己在 App 侧或平台侧实现驱动 —— 这是有意接受的成本，不是遗漏。

于是两条规则正面冲突。本文取代它。

## 决策

### 1. HAL 之上加一层「服务层」，hal::Context 加可空服务槽

分层从两段变三段：

    App（用户写）      ← 业务：天气怎么显示、放哪首歌、下一步是什么
    服务层（基建）      ← 设备服务 + 公共资源：IImu / IAudio / INetwork / IGpio
    HAL（基建）        ← 芯片能力：ITime / IPersistence / ILogSink / ISystem / IBus / IDisplay / IInput

服务本身仍是**接口 + 平台实现**的同构形状（`core/include/embark/hal/<能力>.h` 给接口，
`host/` 与 `device/src/` 各一份实现），只是它站在 HAL 之上、可以持有总线句柄。
装配走同一个入口：`hal::Context` 加**可空指针槽**，语义与 `display` / `input` 同款
（「没有这块硬件就是 nullptr」，而不是「给一个恒 not_ready 的实例」）。

槽的落地见 issue 07；今天先在本文把**规则**定下来，否则下一个人会照 0002 写。

### 2. 硬规则：HAL 里不许出现芯片型号名

**`IImu` 可以，`IQmi8658` 不行。** 同理 `IAudio` 可以、`IPcm5101` 不行，`INetwork` 可以、
`IEspWifi` 不行。

这是 ADR 0002 原意的**延续**，只是把线从「HAL 层」上移到了「服务接口层」：
0002 怕的是「接口被某颗芯片的细节绑死，可移植性反而下降」，这条恐惧到今天依然成立。
所以不是「0002 错了所以要放开」，而是 **0002 的判据没变、适用范围扩大了一层**：

- HAL 层：接口描述「芯片能做什么」（收发字节、刷屏、读时钟），不提具体外设。
- 服务层：接口描述「设备能提供什么能力」（读姿态、放音频、发 HTTP），**不提具体型号**。
- 换芯片 → 换实现，接口与该接口的所有调用方零改动。

芯片型号名出现在哪都行：实现文件、板级头（`device/src/esp32_board.h` 里的引脚与型号）、
注释、文档。**唯一禁止的地方是接口头**（`core/include/embark/hal/*.h`）。

### 3. 明确排除：业务服务不进基建

「天气服务」「音乐服务」这类**带业务语义**的东西不进服务层。
判据：接口里出现「用户看到什么」就出局 —— `IGpio` 进（电平）、`IWeather` 不进（摄氏度与穿衣建议）。

理由不是洁癖，是维护归属：业务是**用户自己写的那一半**。把它塞进基建，等于让 AI 继续维护
用户本来想自己掌握的部分，token 成本又回来了 —— 而这次改造的动机就是省 token。

### 4. 音频分三层，只有前两层进基建

| 层 | 内容 | 归属 |
| --- | --- | --- |
| L1 设备 | 打开 I2S 设备、写 PCM 帧、设置采样率/声道 | **基建**（`IAudio`） |
| L2 流 | 打开一个 WAV 文件、按帧喂给设备、播放/暂停/seek 的位置 | **基建**（`IAudioStream`） |
| L3 业务 | 播放列表、下一首、音量记忆、进度条怎么画 | **用户** |

音量那条有个板上事实必须在接口层就说清：这块板的音量旋钮接的是功放模拟增益，
**ESP32 看不到**（PCM5101 的控制接口是 HW，无 I2C/SPI 寄存器）⇒ `IAudio` 能做的「音量」只有
**软件采样衰减**（每 6 dB 掉 1 bit 有效精度）。接口注释要写这一句，否则调用方会以为能读到旋钮。

### 5. 网络做完整版，但排在姿态与音频之后

`INetwork` 一次做完整（state / connect / http_get / sntp），不做「先 stub 后补」。
理由：网络是最容易做成半成品的一块（连上了但没超时、有 socket 没 TLS），分两次做等于
把半成品固化进接口。但它排最后（批次 5），因为它是唯一依赖外部世界的一块，
验证成本高，且 3/4 批（姿态/音频）不依赖它就能独立验完。

## 被否决的方案

**Q9（基建停在哪一层）**

- **(A) 只做 HAL，公共硬件全归 App** —— 每个 App 自己写 IMU / 音频 / WiFi 的驱动与错误处理。
  否决理由：这正是用户要消除的东西。三块硬件的驱动写 N 遍 = N 份 token，且每份都要重新踩
  同一批坑（I2C 时序、I2S 欠载、WiFi 重连）。基础设施的价值就是「只写一遍」。
- **(B) HAL + 设备驱动（驱动进框架，接口按芯片给，如 `IQmi8658`）** —— 否决理由：接口绑死芯片。
  换板就得改所有调用方，这正是 ADR 0002 当初拒绝的那件事，只是换了个位置犯。
- **(D) 连业务服务一起进基建（`IWeather` / `IMusic`）** —— 否决理由见上「业务不进基建」。
  另外业务接口必然带上「该显示什么」的语义（「5 天预报」是几个控件？什么布局？），
  而界面是用户自己画的，两者会互相绑死。

**Q10（「公共」的判据）**

- **(A) 按「几个 App 用得上」判** —— 否决理由：用几次是今天的巧合，改不了接口形状。
  两个 App 用同一颗芯片也可能各写一套驱动；反过来，今天只有一个 App 用的能力（比如姿态）
  明天可能变成三个 App 都用。判据必须与「用法数量」无关。
- **(B) 按硬件类别判（传感器 / 输出 / 通信）** —— 否决理由：类别不决定接口形状。
  同为「传感器」，IMU 是「持续采样的三轴量」、温湿度是「低频标量」，事件模型完全不同；
  按类别归档必然会催生一个空抽象基类，然后每个实现都在里面塞「用不上但要 override」的方法。
- **(C) 按「接口形状稳定」判 + 禁芯片型号名** —— 采纳。判据变成一个问题：
  「这块能力的接口，换一颗同类芯片需要改吗？」不需要 ⇒ 可以进服务层。

## 代价（写清楚，别当没发生）

- **多一层**：App 读姿态是 `fw.hal().imu->read()`，不是直接摸 I2C。多一跳调用，
  但也多一个可以整体替换、可以整体 mock 的接缝（宿主侧用合成数据验，不需要硬件在环）。
- **可移植性的证明责任转移**：以前「HAL 薄」本身就是可移植性论证；现在服务层也得守同一条规矩，
  靠「接口头里没有芯片型号名」这条硬规则兜住。这条规则**没有编译器约束**，只能靠 review 与
  这条 ADR —— 所以要把它写进 `docs/agents/` 的约定里，让下一个 AI 也会查。
- **池与栈的账要重算**：服务实现自己占栈/缓冲（I2S DMA、WiFi 的 lwIP 堆），
  这些不进 LVGL 的两块池，得在板级的 `device/src/esp32_board.h` 里单独列。issue 08/09/10 各自记账。
